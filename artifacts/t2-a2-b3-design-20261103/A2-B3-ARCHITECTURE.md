Status: PROPOSED, not executable or release-accepted. Founder authorized lightweight design/offline validation on November 3. CoS owns composition and operational authorization; Atlas must review this contract. Base `003dc49ac734317802253d28ee0ecafd4e1ea7fd`. ## A2 roles and ownership

These are PostgreSQL identities, separate from application User roles. All three have NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION and NOBYPASSRLS; bootstrap/runtime have NOINHERIT and no role memberships, including no SET ROLE path to the owner or each other. NOINHERIT alone is insufficient. Inspect every recursive membership and PostgreSQL-version-specific SET/INHERIT/admin option. Neither runtime nor bootstrap may set session_replication_role or execute an elevated security-definer function.

| Role | Ownership / admission | Exact privilege envelope |
| --- | --- | --- |
| `preview_owner` | NOLOGIN owner of application schema, tables, sequences, enums, policies, migration ledger, guard functions and triggers. Controlled operator session assumes it only for separately reviewed DDL. | Owner powers are inherently privileged and cannot be neutralized by ordinary REVOKE. No hosted app credential or bootstrap credential may inherit or assume this role. An existing authorized administrative operator is the migration executor, not a fourth application login. Provider-managed schemas/extensions remain provider-owned and outside this ownership transfer. |
| `preview_bootstrap` | LOGIN only during an authorized initialization or maintenance window; ordinary state NOLOGIN, no active sessions and no data grants. Owns no object. | CONNECT to the isolated Preview database; USAGE on public and required enum types. Phase-specific table grants below, no grant option. Never CREATE/TEMP, schema ownership, TRIGGER, TRUNCATE, REFERENCES, DELETE or general UPDATE. No migration-ledger writes. Credentials private to the operator, never Vercel/runtime. |
| `preview_app` | Runtime LOGIN, owns no database/schema/table/sequence/function. No membership in owner/bootstrap/provider service roles. | CONNECT, USAGE on public and necessary enum types. SELECT on the explicit runtime list below; INSERT on AuditLog under restricted policies. No table UPDATE/DELETE, no sequence access unless an actually used default requires separately reviewed USAGE on a named sequence. No grants on all/future tables. |

Revoke database CREATE and TEMP from PUBLIC and runtime/bootstrap, and CREATE on application schemas from PUBLIC and all non-owner roles. In the separate Preview database, revoke CONNECT from PUBLIC and grant explicitly to required roles/provider operations only after provider review. Revoke application schema/table/column/sequence/function grants from PUBLIC, anon, authenticated and service_role; do not modify provider-owned schemas or cluster-wide roles blindly. Provider superuser powers cannot be revoked by this design and remain a separately assessed trust boundary. Verify provider access/Data API/storage/public network exposure independently.

For every object-creating role, default privileges grant nothing to runtime/bootstrap/PUBLIC/anon/authenticated/service_role. Functions default to no PUBLIC EXECUTE. A future migration receives explicit grants only after its diff is reviewed. Trigger functions remain SECURITY INVOKER, owner-owned, hash-pinned, with no direct runtime/bootstrap EXECUTE grant; trigger invocation is verified on the actual provider/version. No writable schema occurs in a helper search_path. Extension functions get only individually reviewed execution privileges if required. The maintenance inventory uses an explicitly reviewed owner-only SELECT policy, TO preview_owner with USING(current_user = 'preview_owner'), while other application sessions/writers are excluded. Only aggregate counts and safe fingerprints leave that inspection. Remove this maintenance policy and verify the final policy set before bootstrap; FORCE RLS remains enabled. Owner DDL already allows changing policies, so this does not create an application-access exception.

### Exact proposed data grants

This is a closed allowlist, not permission to apply SQL. Quoted names mean `public."Name"`. Each SELECT remains RLS-limited. Unlisted relations receive no grants and default-deny RLS. Before execution, Atlas must bind the list to the final route/query inventory and prove the positive journeys; a denied legitimate query is a blocker, never permission to add ALL.

- Runtime SELECT: School, User, Student, Class, Enrollment, TeacherProfile, Timetable, Assignment, Attendance, DataPolicyAcceptance, PolicyConfig, AuditLog. SELECT on `_prisma_migrations` is permitted only for existing read-only preflight metadata, not application mutation. No runtime SELECT on Grade, MasteryRecord or provenance/history tables is needed by this design; catalog visibility is sufficient for metadata checks. Authentication necessarily reads synthetic password hashes server-side; these must never leave authentication code or enter evidence output.
- Runtime INSERT: AuditLog only, for allowed authentication/access events and synthetic subjects. Runtime cannot insert lesson-release authorization or operator-operation events. All roster, credential, consent, academic and policy writes are denied, including User last-login/PIN/password mutation. If T1 requires last-login updates, T1 must remove them in deployed Preview or submit a narrower alternative for review.
- Initial bootstrap SELECT + INSERT: School, User, DataPolicyAcceptance, TeacherProfile, Student, Class, Enrollment, Assignment, Attendance, Timetable, PolicyConfig, AuditLog. Fixed IDs/relationships and synthetic constraints below apply. No UPDATE even for an upsert conflict. No sequence grants for client-generated IDs; inspect actual defaults before concluding none are needed.
- Re-anchor bootstrap SELECT: same 12 tables. INSERT only PolicyConfig and AuditLog. UPDATE only `Timetable.dayOfWeek`, `PolicyConfig.config` and `PolicyConfig.isActive`, with row policies and OLD/NEW trigger constraints distinguishing the live policy from historical approval rows. No table-level UPDATE; no credential/account/attendance change. SQL UPDATE predicates may require SELECT on columns, already included. No other columns may change except schema-managed timestamps explicitly reviewed in the trigger contract.
- Operator control schema `preview_control`, proposed but not created: owner-owned append-only attempt/event ledger and singleton bootstrap admission. Bootstrap may SELECT/INSERT exact attempt records; runtime has no access. No mutable completion flag: completion is a new unique event committed with the seed. No UPDATE/DELETE/TRUNCATE. This requires an additional reviewed migration and trigger, not covered by the existing 12-trigger inventory.

Bootstrap grants for initial admission and re-anchor are mutually exclusive, revoked after the operation; disable LOGIN and terminate residual bootstrap sessions before runtime acceptance. Password expiry alone does not end an existing connection. An interrupted grant cleanup leaves the release BLOCKED even when fixture rows committed. Owner/operator secrets are never made available to the application or reused as reviewer passwords.

## RLS contract and its limit

ENABLE and FORCE RLS on all application tables, migration ledger and the proposed control ledger. No policy for unlisted tables. Policies name one specific role and command, with USING and WITH CHECK reviewed separately. No PUBLIC policy, ALL-command policy or USING(true)/WITH CHECK(true) exception. Review the complete policy set, because permissive policies combine with OR. RLS does not protect TRUNCATE or defeat a privileged owner; ACLs and owner separation are essential. [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [ownership and privileges](https://www.postgresql.org/docs/17/ddl-priv.html).

Runtime RLS limits data to the two fixed synthetic schools and exact fixture identities from `scripts/e2e/school-day-identities.json`; joins for child tables use fixed accepted parents and exact IDs. The foreign-school fixture remains available for application denial tests. One shared PostgreSQL login does NOT identify the signed-in student/teacher/admin: this RLS is a fixture boundary, not per-session tenant isolation. T1 must still prove auth/role/tenant denial in actual handlers. Do not trust caller-set custom GUCs as actor authority. If database-enforced per-reviewer isolation is required, trusted session binding needs a separately reviewed design; none exists here.

Initial-bootstrap INSERT policies admit only the exact fixture IDs, synthetic names/invalid email domain, fixed school/class relationships, zero-grade/zero-mastery state, fixed package identities and synthetic approval status. Child inserts require accepted parents. All application tables must be empty before first admission, excluding only independently verified migration/control metadata; the existing seed's 12-table emptiness check is not a complete schema-wide contamination scan. RLS-filtered bootstrap/runtime counts cannot prove global emptiness. The authorized owner-side inventory must establish full schema-wide emptiness in a maintenance window with all other application writers excluded, including runtime AuditLog INSERT, background workers and residual connections. Bind its source/schema/plan and snapshot evidence to the attempt; preserve writer exclusion through bootstrap commit. If that exclusion cannot be demonstrated, admission is BLOCKED. Provider administrative access remains an explicit trust boundary. Bootstrap's in-transaction counts are an additional check, not a substitute for that owner evidence. FORCE RLS also filters a non-bypass owner: the reviewed owner inspection plan must explicitly provide full row visibility in the maintenance window, restore default-deny policies before bootstrap, and retain evidence of that transition; no unreviewed USING(true) exception is permitted.

Re-anchor policies admit only the existing synthetic school/class/eight periods and approval-ID namespace. An OLD/NEW guard must enforce: historical approval config/ID/creator/school/key are immutable; only active true to false is permitted for superseded approvals; the live policy alone can receive a new validated config; new approvals/audits must match fixed sealed hashes and the allowed 24-hour window from UTC today through +14 days. SQL role and prefix checks alone cannot certify package semantics: bind reviewed inputs and verify all stored bindings. Granting UPDATE(config) without this guard is unacceptable.

## Migrations, db push and operational setup

The repository uses Prisma 6-era migration files and CLI behavior. Reviewed migrations carry schema SQL plus custom triggers/RLS/grants and checksummed `_prisma_migrations` history. A controlled migration executor assumes preview_owner to apply a reviewed, ordered plan. Before approval, rehearse the entire repository chain against an isolated empty DB with the frozen client/engine and extension prerequisites; successful application and complete checksums are not yet proven here. Do not generate, reset, baseline/resolve, or repair history against a hosted DB automatically.

`db push` synchronizes schema.prisma without replaying the custom migration SQL or producing its migration history. It cannot establish these trigger/RLS guarantees. The current setup wrapper runs db push as preview_app and the seed and re-anchor guards require that username. Therefore all three are incompatible with the proposed split and must be adapted and reviewed before A2. Do not change the pinned `preview-target.mjs`; design a separate reviewed bootstrap-role validator later, preserving exact URL rejection behavior. Changing a database role name in an operator file to evade the guard is prohibited. Operational initialization is synthetic DML after accepted schema installation, not a migration. PV-05 is later synthetic maintenance, not initialization. [Prisma CLI reference, migrate deploy and db push](https://docs.prisma.io/docs/orm/v7/reference/prisma-cli-reference) documents the command distinction; use the repository's pinned 6.19 CLI for any future rehearsal, not documentation's newer release defaults.

## B3 initial admission and reruns

| Observed state | Required disposition |
| --- | --- |
| No local receipt/lock, no control admission/events, accepted schema/roles, every application table empty | Eligible for a separately authorized first bootstrap, not automatic permission. |
| Local STARTED/FAILED/SCHEMA_FAILED/SEED_FAILED, lock only, malformed receipt, unknown commit outcome or any nonempty application state without matching committed ledger | STOPPED/UNKNOWN. Preserve everything; no seed retry, cleanup or reset. |
| Schema installation partially failed / migration ledger incomplete | Owner-side reconciliation only under a new reviewed plan. Never seed and never use db push to hide drift. |
| Database COMPLETE ledger plus matching exact fixture/binding hashes, role cleanup, source/lock/plan hashes and local receipt | Read-only ALREADY_COMPLETE acknowledgment only; no credentials revealed/rotated, no audit upsert or data rewrite. |
| DB COMPLETE but local receipt absent/stale, mismatched cardinality or credentials lost | STOP. Read-only reconciliation first. Reconstruct a receipt only under separately reviewed authority after binding the committed operation; never reseed to recover credentials. |
| Explicit authorized PV-05 re-anchor of intact COMPLETE fixture | Separate maintenance transaction; no initialization grants and no bootstrap rerun. |

Proposed transaction protocol: create a unique local attempt/STARTED receipt before connection; owner-controlled phase records append-only attempt provenance. Bootstrap transaction takes the existing bootstrap advisory transaction lock plus a unique database singleton admission constraint, runs Serializable isolation, scans all application tables for contamination, verifies schema/roles/guards and fixed synthetic manifest, inserts all fixtures and a COMPLETE ledger event in the SAME transaction. Bounded timeout. Existing `upsert` calls need conversion to insert-only initialization: even an empty expected fixture does not justify UPDATE privileges on User/AuditLog. No automatic serialization retry. Concurrent contenders produce one winner; the loser stops for reconciliation. Migration DDL, role grants/revocation, console credential delivery and local file writes are separate phases and cannot share the DML rollback guarantee.

After verified commit, revoke bootstrap grants, disable login/end sessions, recheck runtime catalog contract and fixture hashes, then persist local COMPLETE and reveal only the three approved reviewer credentials in the private console. A commit followed by lost response, console failure or disk failure is UNKNOWN, never safe-to-retry. Secret delivery is not transactionally recoverable; operator-approved credential recovery is a separate plan and must not regenerate the fixture. Do not silently equate a local COMPLETE record with current DB acceptance, as the current wrapper's fast path does.

Recovery procedure: freeze access; preserve local receipts/lock/evidence and DB snapshot/provenance under approved read-only scope; identify project, exact operation, role sessions, ledger/migration state, synthetic counts/bindings and before/after history. CoS/Atlas classify committed, rolled back or unknown. Operator submits exact forward-only reconciliation SQL or receipt-reconstruction action, safe outputs, rollback limits and credential treatment to founder. Only fresh authorization executes it. No deletion/reset/schema drop on populated DB, no overwritten audit/approval history, no automatic lock removal and no reusing A1b partial-write recovery authority. A truly new empty Preview database is a separate infrastructure decision, not a silent escape path.

PV-05 successor `1ca443b4` already creates eight new approvals/audits, repoints the live policy, deactivates old approvals without config rewrites, and appends operation provenance. Same-date invocation preserves fixture/approval/timetable state but APPENDS an operation audit, so it is data-idempotent only for those named objects, not globally side-effect-free. Fresh date needs explicit operator input in UTC today..+14, exactly 24 hours, same sealed packages. Preserve all historical configs and all audit bytes. Later role/guard integration must not recreate this implemented revision.
