# Internal Security Review — 2026-08-10

**This is NOT the P1-D external penetration test.** It is a compensating
measure only, performed because no budget currently exists to contract an
independent vendor (see `docs/security/PEN_TEST_VENDOR_ENGAGEMENT.md`,
whose status remains unchanged: no vendor selected, no engagement
contracted). The reviewer (Claude Code) shares engineering context and
possible blind spots with the team that built this codebase, which is
exactly the property an independent test exists to avoid. P1-D's
external-pen-test deliverable is still fully outstanding after this
document. Treat findings here as a useful interim signal, not as
assurance equivalent to third-party validation.

**Scope:** the P0 and P1 attack-surface priorities already defined in
`docs/security/PEN_TEST_BRIEF.md` (10 items). P2 items were not reviewed.
**Method:** static code analysis of the `main` branch by a Claude Code
subagent (Read/Grep/Glob only, no live traffic generated by the subagent),
plus independent live spot-checks against production by the coordinating
session (unauthenticated requests to `/admin`, `/platform`,
`/api/admin/students`, `/api/moe/dashboard`, `/api/student/results`,
`/api/guardian/student/[id]`, and the certificate verify page — all
behaved correctly) and a direct read of the one CRITICAL finding's source
file plus a grep for any consumer of the JWT it issues, both confirmed
independently rather than taken on the subagent's word.

## Findings

### #6 — CRITICAL: `/api/auth/login` unauthenticated brute-force oracle + hardcoded JWT secret

File: `app/api/auth/login/route.ts` (full file, ~90 lines).

Two independent problems, independently re-verified by the coordinating
session (not just the subagent):

1. **No rate limiting at all.** The route calls `bcrypt.compare()` against
   any email's real `hashedPwd` with zero call to `checkRateLimit` or any
   equivalent. An attacker can attempt unlimited password guesses against
   any known email address (student, teacher, admin, MOE official) with no
   throttling. Confirmed by reading the full route body — no rate-limit
   import or call exists anywhere in the file.

2. **Hardcoded JWT secret fallback, and it is the live one.**
   ```ts
   const secret = new TextEncoder().encode(
     process.env.JWT_SECRET || 'your-secret-key-change-in-production'
   );
   ```
   `JWT_SECRET` is confirmed **not set** in production Vercel env
   (`vercel env ls production` has no `JWT_SECRET` entry) — the fallback
   string is the actual live signing key for any JWT this route issues.
   `PEN_TEST_BRIEF.md`'s own known-fixed table lists "S16B | Hardcoded
   JWT_SECRET fallback in login route | Sprint 16B" as already fixed; the
   fix did not reach this file.

**Practical exploitability, independently checked:** a grep across
`app/` and `lib/` for any reader of the `token` cookie this route sets, or
of `JWT_SECRET` itself, found nothing — no route or middleware trusts this
cookie today, so the forged-JWT angle is currently inert. `lib/auth.ts`
and `middleware.ts` only ever trust the NextAuth
`__Secure-next-auth.session-token`. This means the JWT itself is currently
a dead end. **The brute-force angle is real and live regardless**: a
successful guess against this endpoint recovers a real account's actual
password (verified via the same `hashedPwd` field the real login uses),
which then works against the legitimate NextAuth login too. The endpoint
is publicly reachable (exempted by the `/api/auth/*` public-path rule in
`middleware.ts`).

Recommended fix: delete this route if it is genuinely dead code (a grep
found only a unit test referencing it, no production frontend caller), or
if it must stay, add the same rate limiting the NextAuth credentials
provider already uses and remove the hardcoded fallback secret entirely
(fail closed if `JWT_SECRET` is unset, don't silently use a public
string).

### #2 — HIGH: cross-school grade override IDOR

File: `app/api/grading/[submissionId]/override/route.ts`.

`requireRole("TEACHER", "ADMIN")` gates the route, but the subsequent
`GradedSubmission.findUnique({ where: { id: params.submissionId } } )`
and the follow-up `update()` never check that the submission's student
belongs to the caller's school. A TEACHER at School A can `PATCH` a
guessed or enumerated `GradedSubmission` ID belonging to a student at
School B and overwrite that student's score and feedback.

Recommended fix: before the update, resolve the submission's owning
student and verify `student.user.schoolId === user.schoolId` (matching
the pattern already used correctly elsewhere, e.g.
`app/api/teacher/assignments/submissions/[submissionId]/grade/route.ts`).

### #3 — MEDIUM: MOE school-cohort export missing small-cohort suppression

File: `app/api/moe/export/school/[schoolId]/route.ts`. Returns one
pseudonymized row per student (SHA-256-truncated ID, grade, band, exam
average, attendance, intervention flag) with no check that the cohort is
large enough to prevent re-identification (no n&lt;5 suppression, unlike
the pattern MOE aggregate exports are supposed to follow per
`PEN_TEST_BRIEF.md`'s own P0 framing). Also no check that the requested
`schoolId` falls within the calling MOE user's authorized
district/county scope. National and district-level exports were checked
and are aggregate-only — this is specific to the school-level export.

### #8 — MEDIUM: some secondary rate limiters trust raw `X-Forwarded-For`

The primary auth rate limiter (NextAuth credentials login) keys on the
account identifier, not IP, and is not affected. Several secondary
limiters (`/api/enroll`, `/api/auth/forgot-password`,
`/api/auth/reset-password`, `/api/register/student`,
`/api/register/guardian`) key on `X-Forwarded-For` instead of Vercel's
non-spoofable `x-real-ip` / first-hop value. On Vercel this is lower risk
in practice than it looks (Vercel prepends the real client IP), but
`/api/enroll` reads the full raw header value without normalizing to the
first entry, and `forgot-password`'s IP-based policy (200/hour) is loose
for a password-reset flow.

### #5 — LOW/INFO: certificate verify page discloses first name

Intentionally public by design (`middleware.ts` `PUBLIC_PATHS`); returns
only `studentFirstName`, a subject/lesson title, and a date — no full
name, school, or grade. A documented tradeoff for third-party credential
verification, not a bug, but worth naming explicitly in the privacy
policy as a deliberate minimal-disclosure decision.

### Mitigated (no action needed)

- **#1** Horizontal privilege escalation across student-facing routes —
  every route checked anchors data to the session's own user/student ID.
- **#4** Auth bypass on `/admin/*`, `/platform/*` — independently
  re-verified live: unauthenticated requests to `/admin` and `/platform`
  return `307` redirects to `/login`; `/api/admin/students` and
  `/api/moe/dashboard` return `401`.
- **#7** Google SSO invite bypass — new accounts require a valid, unused,
  unexpired `SSO_INVITE` matching the exact email; non-TEACHER existing
  accounts cannot use SSO at all.
- **#9** Teacher access to a student outside their own classes — requires
  both school match and an explicit `Enrollment` link to one of the
  teacher's own classes before returning any data. (The brief's literal
  `/api/student/results` URL does not correspond to a real route; the
  equivalent real student-facing routes are covered under #1.)
- **#10** Guardian–student link confusion — every guardian route checked
  requires a `StudentGuardian` link record before returning any data;
  none trust a client-supplied `studentId` alone.

## Caveats (carried from the reviewing subagent, endorsed after
independent spot-checks)

1. Not an independent third-party test — same engineering context as the
   codebase, real blind-spot risk.
2. Static analysis only for the subagent's portion; live spot-checks in
   this document were limited to a handful of unauthenticated GETs, not a
   full dynamic test.
3. Only P0/P1 items reviewed; P2 (SMS webhook spoofing, cron secret
   enforcement on all 24 routes, file upload abuse, AI prompt injection,
   DB-layer audit log immutability) not covered here.
4. Coverage within reviewed categories is not exhaustive — e.g. only a
   subset of the roughly 80 `/api/teacher/*` routes were read.
5. `PRIVILEGED_MFA_ENFORCEMENT_ENABLED` is off in production; the P1-C
   step-up/MFA bypass scenarios in the brief are not reachable today and
   were not tested here — they need testing once that flag is staged on.
6. The S16B "hardcoded JWT_SECRET fallback" fix was specifically
   re-examined because code evidence contradicted the claimed-fixed
   status in `PEN_TEST_BRIEF.md`; other rows in that table were not
   independently re-verified in this pass.
