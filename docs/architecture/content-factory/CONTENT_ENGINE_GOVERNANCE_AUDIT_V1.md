Audit date: 2026-10-13. Requested base: `main`. Exact audited source: **`f22ccb7bbfb8b7f57ab6ebd3ff7b7ae2f2e445f1`**. Audit branch: `docs/content-engine-governance-audit-v1`, based on that commit; no commit, merge, deployment, publication, schema implementation, hosted reads, hosted writes, paid generation, or migration was performed.

Local `main` resolved to `223ed86a2fc5f53b9117d939dca01dc8523a608c`, not the expected commit. The requested commit was available locally. Inspection and focused tests used a `git archive` snapshot under `.task-evidence/content-audit-f22ccb7`; the audit branch/worktree was created separately under `.task-worktrees/content-engine-governance-audit-v1`. This document is also placed at the requested shared-checkout path for review. Shared changes were not incorporated into the audit. Consequently findings describe the requested SHA, not current main, current uncommitted work, or a deployed database.

**Recommendation:** ContentBundle should be a versioned, typed composition manifest over existing curriculum revisions, ontology release bindings, governed items, certified lab versions, toolkit policies, and derived resources. It must not become another approval, release, grading, mastery, or provenance engine. Curriculum V2 provides the best candidate/assembly boundary; the existing curriculum mutation/review system provides lineage and human authority; the published ontology registry, governed inventory, evidence contract, canonical mastery writer, Student Learning Model (SLM), DecisionModel, and Learning Orchestrator provide the executable learning chain.

Existing first-class delivery and student-state models should remain first-class. Bounded, strictly validated instructional documents can remain versioned payloads inside `CurriculumContent` and its immutable revision snapshots. Cross-object references, lifecycle, authority, audience, and student state must not be hidden in a giant untyped bundle payload.

Repository status is not deployment evidence. A schema model or migration file establishes an implementation contract, not proof that hosted migrations ran. A generated artifact, `APPROVED` string, or source citation does not establish MOE approval, certified laboratory access, or canonical mastery.

### Explicit Project and Classwork answer

There is **no model named `Project`** and no general reusable project-definition model. There **is** `CapstoneProject`, a student work/lifecycle model. Projects also exist as `projectTask`, NR-13 `studentMaterials.project`, and `PROJECT` component/evidence types. Those representations must not be mistaken for assigned capstones.

There is **no first-class `Classwork` model**. Classwork appears as embedded activities/materials, `ComponentKind.CLASSWORK`, `GovernedEvidenceType.CLASSWORK`, and the assignment-generator type string.

Represent **CLASSWORK and PROJECT as typed reusable content-definition kinds and version-pinned bundle bindings** first. Reuse `CurriculumContent`/revisions for bounded activity definitions (instructions, objectives, materials, rubric reference, expected artifact, collaboration mode). Reuse Assignment/ScheduledWork for class deployment and responses, and CapstoneProject/PortfolioItem for sustained capstone student artifacts. No new Classwork table is needed for V1. Defer a dedicated ProjectDefinition/ProjectMilestone or ClassworkInstance model until real workflow needs such as group membership, milestones, distinct submission lifecycle or relational reporting exceed existing models; any such model should reference the same curriculum revision/governance system, not introduce another authority ledger. Due dates, classId, group members, learner files and scores belong to instances, not bundle definitions.

## 3. Authority boundaries and factory safety

### Existing boundaries to preserve

1. Source-authoritative curriculum wording comes from verified source/version/objective records and the structured-source contract. A subject catalog, prompt, framework tag, inferred concept, or WAEC code is not MOE approval.
2. Candidate generation may propose instruction, formative feedback, activities, lab requests and assessment requirements. It may not supply governance state, publication, scoring policy, answer-release permission, canonical mastery or next action.
3. `repository.ts` separates nonauthoritative content writes from governance writes. `assertContentWriteIsNonAuthoritative` rejects APPROVED/PUBLISHED/edit approval/publication timestamps even with writers disabled. Native structure requires provenance writers and native approved instruction is protected against replacement. Native snapshot schema 2 captures whole scene structure.
4. `governanceWriter.ts`, reviewer eligibility and `review/decisions.ts` authorize the exact revision, identified human and qualification scope. Native V2 disallows automated/role/school/AI approval. Legacy policy exceptions should not be inherited by bundles.
5. `CurriculumVersion.ACTIVE`, curriculum lifecycle approval, registered published ontology release, learner-safe projection and tenant/enrollment access are different gates. Bundle assembly must require the applicable intersection, not choose whichever legacy status permits delivery.
6. Only existing assessment authority scores trusted keys. Only admitted governed evidence enters `masteryWriter` and SLM. Only existing DecisionModel/orchestrator resolves next action. Artifact flags and learner client state cannot bypass these boundaries.

## 4. Textbook compiler audit

`textbookCompiler.ts` reads `CurriculumUnit` ordered by weekStart/createdAt, then `CurriculumContent` lessons whose status is exactly `APPROVED`. Direct unit soft links take precedence; if none exist, it scans matching grade/subject lessons and infers week from payload or content ID. This can omit `published` lessons, include status-only approvals, mix mutable input versions, and infer inclusion without approved objective/revision membership. School filtering is applied to units; fallback lesson queries have grade/subject but no school filter. A school label defaults to “Ministry of Education, Liberia”; that branding must not imply MOE endorsement.

The compiler returns structured `TextbookResult` and optional streamed cover/unit/lesson/summary text. React PDF produces downloadable PDF; queue uploads PDF via storage helper. This is compilation, not a separate model-based textbook-writing authority. Estimated/“actual” page counts in compiler are word-based estimates, not measured PDF layout. Four logical formats are declared: student, teacher, workbook, assessment. **Only student is implemented with lessons:** `format !== 'student'` returns an empty result. Queue accepts other formats and can still render/upload their empty result, so GENERATED status does not prove substantive teacher/workbook/assessment support. No EPUB/DOCX implementation was found in this compiler.

`CompiledLesson.answerKey` comes directly from `payload.answerKey`. `renderLessonSection` and `textbookPdf.tsx` render it without audience gating. Lesson body can also contain teacher/answer prose. Existing student projection is not used here. Question arrays are duplicated lesson prose/string lists rather than versioned assessment references.

Target: compile student text, workbook questions, teacher notes and assessment sheets from the **same resolved ContentBundle revision/dependency set**, after release eligibility. Student/workbook exports receive learner-safe sections and approved practice disclosures; teacher guides and secure keys require staff authorization. Each output records compiler version, audience, bundle/release identity, source revision hashes, ordered section references, asset rights/accessibility, output digest and revocation/offline expiry policy. Output job remains `TextbookGenerationJob`; it never approves its sources or publishes curriculum. No export of secure keys is permitted merely because format is `assessment`.

## 5. Assessment architecture and Assessment Player V2 dependencies

### What exists

There are several assessment representations, not one unified bank:

- School Exam/ExamQuestion and publication/results administration; deterministic `gradeAttempt` compares positional answers and awards points. Student start checks school/grade/class enrollment/year membership, but positional arrays with unordered `questions:true` are weaker than frozen item-ID ordering.
- PracticeItem/Assessment/AssessmentItem/Submission with server-side JSON keys and rubric storage; incomplete lifecycle/version authority.
- Generated lesson quizzes with preauthored-five-item override, user/lesson-bound encrypted session and allowlisted pre-submit questions; AssessmentAttempt and Detail record scoring. Quiz completion updates legacy unit mastery/certificates/action signals, not the canonical governed item release automatically.
- Generated adaptive practice sessions and WAEC DB bank; server-hidden key transport exists, while reviewed item authority is missing.
- Curriculum V2 formative lesson checks. `formativeKey.expectedOptionId` permits instant local feedback in formative scenes. Candidates may request ASSESSMENT_HANDOFF; server resolves release-safe item IDs/versions/prompts/options. Handoff exists before Assessment Player V2 exists.
- Existing `GovernedItem` is single-choice with correctIndex, immutable ID/version and DIAGNOSTIC/PRACTICE contexts; construct bindings attach concept/skill/standard/learning target/evidence and tool policies. `admitEvidence` and `toCanonicalMasteryEvidence` validate release/item/policy/scope, then writer rescores from the server key.

Current canonical conversion accepts scored PRACTICE/QUIZ/DIAGNOSTIC mapped to governed single-choice item semantics. Essay, project, numeric, multi-select and lab observation scoring require reviewed adapters/extensions; no blanket “score > threshold” adapter.
- `mayReleaseStudentAnswer` offers NEVER/AFTER_COMPLETION/AFTER_TIME with tenant/enrollment checks; its existence does not prove all routes/exporters use it.

## 6. Lab architecture and certification

Interactive V2 definitions are code-registry assets, not Prisma rows. They include versioned objects/actions/checks, objectives/concepts, release binding, review/approval and accessibility/fidelity/offline capabilities. Kernel validates/accepts actions and restores checkpoints; evidence evaluator recomputes checks from server state. Practical definitions may be stored in VirtualLab JSON; legacy typed simulations live in `lib/labs/registry.ts`. LabSession is student state and must be outside the bundle.

`LearningExperienceLink` provides exact lesson/version→lab/version, placement, requirement, pre/post scenes, objective/check evidence mapping and independent approval. V2 generation produces only CANDIDATE links with RAW_OBSERVATION mappings. `resolveLabProposal` checks exact objective, grade, known prerequisites, scene and actual check IDs; subject/title matching cannot substitute. `labLinkEligibility` checks link/lesson/definition release/version/grade, but certification is an additional gate.

At the audited SHA, **`CERTIFIED_STUDENT_LAB_VERSIONS` is `{}`**. Legacy simulations are DRAFT_UNRELEASED/LEGACY_UNCERTIFIED; practical presentation is ASSIGNED_ONLY and has no national objective identity. Solids learning-check mappings are PROVISIONAL with pending release identity/policy. `adaptLabEvidence` can convert only an explicitly canonical mapping with matching real release/activity and server result; `masteryAdapter` uses existing canonical writer. Ordinary learner event route currently returns `mastery:'not_mutated'`; provisional session updates keep `masteryUpdated:false`.

Bundle lab bindings must include immutable link revision/hash; lesson and lab ID/version; objective/concept/check references; practical versus interactive runtime; safety/equipment/accessibility/offline fallback; requirement; approved evidence mapping/policy and resolved certification record. A lab executes for ordinary learners only after all applicable gates pass: approved lesson revision, published curriculum binding, approved link, exact definition, real release identity, exact certified student version, scope/grade/prerequisites and deployment access. Practical teacher assignment must be represented honestly as local assigned practical instruction; it does not confer interactive certification or canonical mastery. Required uncertified lab blocks executable bundle delivery unless a separately reviewed objective-preserving fallback satisfies release requirements.

**SHOWCASE is separate.** `showcaseLabs.ts` verifies a specific persisted demo-school/student identity and keeps unreleased metadata truthful. This access is not bundle eligibility, certification, release or evidence authority; ordinary interactive evidence endpoint still requires certification. Never copy a showcase allowlist or mode into bundle governance. Preview/showcase observations cannot be promoted into canonical evidence.

## 7. Toolkit binding design

Reuse `TOOL_REGISTRY_DEFINITIONS` and `getToolsForContext`, V2 `toolFitsContext`/`resolveToolAvailability`, and existing release ToolPolicy. No Prisma toolkit-binding model exists; ScheduledWork.toolUsageLog and telemetry are usage state, not permission. Context supports grade band, subject, lesson type and optional strand. Some canonical subjects are not supported by toolSubject; those gaps must remain explicit.

Proposed binding: `{bindingId, version, scopeRef, toolId, registryRevision, requirement, config, context, toolPolicyRef}`. `requirement` is REQUIRED/OPTIONAL/PROHIBITED; context contains objective/concept/activity/scene/strand IDs, never a copied tool implementation. `config` is a bounded tool-specific discriminated schema (e.g. number-line domain/step or fraction allowed denominators), validated by that tool's contract; no `Record<string,any>` code or executable instructions. Pin configuration hash in bundle revision. Required tool has reviewed fallback; prohibited wins over optional/required requests. Configuration cannot expose assessment answers or enable remote URLs/executable scripts.

Availability intersects registry/context, enabled server flags, release assessment policy and authorized accommodations. Client context/query parameters and `defaultOpen` are presentation only. Legacy semantic tool keys require explicit mapping already anticipated by `templateCell.ts::CertificationInput.releaseToolKeyMap`; preserve immutable old policies and introduce reviewed mappings/new policy versions instead of rewriting old release identity. Lessons declare purpose/binding refs; toolkit implements behavior.

## 8. Proposed technical ContentBundle contract

### Composition and persistence

This is an architecture proposal, not implemented TypeScript or Prisma. A bundle is scoped to one reviewed grade/subject/unit/objective slice; a larger unit/course composes bundle refs. Empty collections mean no binding, not generated filler. Missing required bindings yield explicit gaps/non-executable status. Authoring a bundle against a published base release does not release the new components.

Names not already implemented above are proposed strict interface types. Existing release item/binding types should be imported/adapted, not copied into a new bank. `BundleIdentity` comprises stable bundle/contentId, semantic contract/contentVersion, exact current CurriculumContentRevision ID/hash/schema, grade/subject/unit and locale. Different pedagogical meaning creates a new revision and review; different published dependency graph creates a new release identity. Version strings alone are insufficient.

Preferred initial storage is a `CurriculumContent` row with contentType `content_bundle` and a **strict composition-only payload**, governed through the same provenance root/revision/events. The payload stores only bounded typed binding lists/config/section plans and existing IDs. Generated lesson bodies and assessment keys remain in their owning definition; class/schedule/student rows remain relational. Persist relational bundle→revision/item/lab binding records when cross-object integrity/query needs demand them; they are linkage extensions, not a second release or lineage model. A JSON manifest is acceptable only if validated against exact existing refs, snapshot-complete and immutable after approval; not an arbitrary data container. The current schema cannot enforce all pins, so final schema choice needs an explicit migration design later.

### Resolution and governance invariants

- One strict candidate contract per content kind; generators cannot populate resolved governance, certification, release, grade or mastery fields. Assessment key candidates remain private until review.
- Bundle revision hash covers complete composition, placement, source/item/lab/policy pins, toolkit config, section plans and accessibility/offline requirements. Extend existing snapshot/hash code when implementing; legacy snapshot schema 1 must not silently omit bundle fields.
- Review package expands dependencies and shows exact revisions/keys to authorized reviewers. A reviewed bundle does not implicitly approve an unreviewed child. Child revision change invalidates composition resolution and requires a new bundle revision/release.
- Existing lifecycle/reviewer writer authorizes each component and composition. Existing published registry validates executable dependency graph; extend its binding kinds/manifest metadata deliberately. No bundle `publish()` engine and no independent `bundleApproved=true` authority.
- Distinguish AUTHORED_DRAFT, REVIEWED_REVISION, REGISTERED_RELEASE and LEARNER_ELIGIBLE as derived facts; do not collapse them into one mutable status. MOE source, platform/founder review and MOE approval are independently evidenced claims.
- Resolve against exact release and revision; validate duplicate IDs, cross-scope refs, missing dependencies, stale hashes, prerequisite cycles and unknown items/tools/checks. Do not infer refs by title, grade, slug or first available concept.
- Use common safe projection across player, tutor, audio, textbook, workbook, offline ZIP and downloads. Public formative examples are different from private summative keys; field allowlists and text review both matter.
- Keep student responses, completion, grades, accommodations, mastery and next decisions in existing instance/event/state systems. Secure assessment attempts are not exported inside content definitions.
- Reuse revocationWriter's replacement/future/existing assignment/offline policies. A withdrawn source/component prevents fresh execution; historical attempts retain exact identity and explain their authority at collection time.
