## Read-only inventory

Use the dedicated [read-only production inventory procedure](../../ops/CONTENT_FACTORY_V2_READ_ONLY_PRODUCTION_INVENTORY.md) and an approved operator's connection. Do not infer credentials from `.env` files or run a writer/seed. Capture a consistent snapshot under a database-enforced read-only, repeatable-read transaction. Inventory every production `CurriculumContent` lesson by database id and logical contentId, grade, subject, status and version. Left join `CurriculumProvenance.currentRevisionId` to `CurriculumContentRevision`, retaining the revision id, sequence, snapshotSchemaVersion, contentSnapshot and contentHash. A missing provenance/revision must remain a gap, never be backfilled during inventory.

Record reference counts/digests from ScheduledWork and the existing assignment, submission and learning-event stores without exporting pupil identities, response bodies or grades. Record the exact query revision, timestamp, environment attestation and file SHA-256 outside the repository. Keep the original export restricted. A read-only query cannot change content, assignments, submissions or events.

It reports missing/tampered revisions and never selects them. It accepts only the exact grade/subject/content-type candidates for the Grade 7 mathematics pilot. The first eligible database id is a deterministic proposal for human selection, not an academically approved choice. The current report explicitly states `NOT_PERFORMED_BY_FACTORY` for live verification.

Run `npx tsx scripts/content-factory-v2-inventory.ts <restricted-export.json> <local-report.json>` against that export. The command only reads its input and creates a new output file with exclusive creation. It imports no database client and has no database write path. The export contains `schemaVersion`, `environment`, `capturedAt`, `queryRef` and `lessons`; each row contains the fields documented above plus `relationshipCounts` for assignments, submissions, learningEvents and scheduledWork. ## Explicit release handoff

No bulk publish, production migration, historical overwrite, old-content deletion or official academic write is part of this mission. Release requires separate explicit human authorization through existing governance. Future integration must keep original lesson IDs and revisions readable, and keep historical assignments, submissions, attempts and learning events pinned to their original revisions. Use a new candidate identity for replacement content; preserve the old identity as provenance rather than reassigning it.

Only future assignments may opt into a separately reviewed bundle revision through the existing content-persistence/ScheduledWork path. Reconnect and offline consumers must recheck exact release/revocation and entitlement. Do not silently rebind cached packs. Historical scores and learning evidence retain their original release identity and standing. Rollback means stop future use of the new release through existing revocation, not rewriting collected evidence or restoring rows in place.

Before authorizing a pilot, rerun read-only counts/digests and compare assignment, submission, event and revision relationships with the baseline. Any difference needs an explanation from normal application activity; the migration tool itself must have no writes. The current pure fixture proves local preservation mechanics, not production preservation.
